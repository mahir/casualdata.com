# casualdata daily: the next version

This branch (`daily`) turns casualdata.com into a site that publishes one interactive data visualization a day. The 2007–2011 work stays in place and is linked from the home page. Everything new lives in new paths, so this branch does not touch the archive redesign on `main`.

## Brand (decided 8 Nov 2026; see PRODUCT.md)

- **Logo `{c} casualdata`, mark `{c}`.** Braces around a c with a level slot, then the name; the same every day, black and white, and it never carries a date (the user's choice on 2026-11-19, replacing `{casualdata}` and `{•}`). The mark alone is used where the name does not fit: the favicon and the top bar under 400 px. Files in `kit/`: `wordmark.svg` and `mark.svg` for the black page, `wordmark-light.svg` and `mark-light.svg` for the white one, `favicon.svg`. They are written by `python3 .impeccable/brand/build/mark_c.py --install` (the script and its two source outlines live only in local copies, since `.impeccable/` is not published). After changing them, update `WORDMARK_RATIO` in `kit/cd.js` and the `width`/`height` on the logo images in each page if the proportions moved, then run `python3 tools/seo.py`, which also gives the daily pages' tab-icon link a new address so browsers drop the icon they have cached. The ten archive pages' icon link (`/favicon.svg?v=…`) is not stamped by the script: change its `?v=` by hand if the root `favicon.svg` ever changes.
- **Day and night.** The page is white from 07:00 to 18:59 by the reader's own clock and black otherwise. `kit/theme.js` runs in `<head>` before the stylesheet, sets `data-theme` on `<html>`, checks again every minute and sends a `cd-theme` event so canvases redraw. `?theme=light` or `?theme=dark` forces one. Every page loads it.
- **Colors.** Day: page `#FFFFFF`, ink `#121212`, red `#E8341C`. Night: page `#0E0E0E`, ink `#EDEBE6`, red `#FF5A3D`. Data is drawn in grey tones between page and ink. Canvas code reads the colors from `CD.colors`, which follows the CSS tokens.
- **The one red thing.** Each visualization uses red for exactly one idea: the point that matters (today, the reader's selection, the outlier). Red marks and large labels only, never running text. **On a chart about political parties the accent is green instead** (`CD.colors.green`: `#0E9F6E` by day, `#3DDC97` by night), because readers take red for Republican; the parties stay in ink and greys (the user's decision on 9 Nov 2026).
- **Type.** Host Grotesk for titles and text. IoskeleyMono (an Iosevka build, OFL-1.1, `fonts/OFL-IoskeleyMono.txt`) in caps for numbers, dates, axes and labels, subset to latin and latin-ext as `fonts/ioskeley-mono-*.woff2`. Fragment Mono stays in `fonts/` for the archive pages.
- **The date is the identity of a day,** never a number: it sits in the top bar beside the logo and on every shared image.

## Navigation (8 Nov 2026)

- **Home (`/`) is every day as a grid,** newest first: the newest takes a full row with its intro, the rest follow three across as tiles of a picture, the date and the title. Drafts are left out unless the URL has `?drafts`. A tile's picture is the day's chart as its page draws it on a small screen, with its own numbers and labels and no headline, in the reader's theme: `thumb.webp` and `thumb-1200.webp` by day, `thumb-night.webp` and `thumb-night-1200.webp` by night, with the first four loaded at once and the rest lazily. The newest day's large tile shows `lead.webp` or `lead-night.webp`, the same chart laid out larger, above 600px.
- **On a day page,** the top bar holds the logo (home), the date between ‹ and › (previous and next day, built by `kit/cd.js` from `kit/days.js`), All days (home) and Share. On phones (720 px and under) the arrows move to a bar at the bottom: previous day · All days · next day, each at least 44 px tall. A draft steps through drafts too.
- There is no menu panel any more; the archive is linked from the home page's top bar and footer.

## How a day works

- URL: `casualdata.com/YYYY-MM-DD/`, a folder named for the day's date at the root. The query string holds the reader's selection (for example `?d=200&lat=-34`), so a shared link opens the same view.
- One screen: `body.cd-day` is a 100dvh grid made of a bar, a head (title, dek and live readout), the stage (a canvas) and a footer (source). The stage keeps a minimum height (`--stage-min`); when the screen is too short for it (large text, a phone on its side) the page scrolls, and the phone bottom bar stays pinned.
- The canvas is `role="application"` with `aria-roledescription="interactive chart"`, and its `aria-label` says what it shows and which keys move the reading.
- Share sheet (`kit/cd.js`): copy the link, the native share sheet (with the image attached where supported), and PNG downloads at 1080×1350 (4:5) and 1600×900 (16:9). The image holds only the visualization and one foot line: the `{casualdata}` wordmark at the left and the date at the right. The day's code supplies `CD.exporter = { draw(ctx, x, y, w, h, scale) }` and the kit adds the date line.
- **The image has no title, so the chart states the point.** Every piece writes its one takeaway into the drawing (a count like "30 of 31 moved left", or a fact on the red mark), so the shared image makes sense on its own.
- **Opening motion: every day opens with one small movement** (the user asked for it back on 21 Nov 2026; the days from 12 Nov on had stopped moving because the model day had no motion, so no copy of it had one). Once on load, in about a second and a half, the marks arrive the way the data runs: a line drawn through its dates, bars rising in order, dots counted in, a boat sailing to its mark. Labels that depend on the marks fade in after them. In `viz.js`, `grow` goes from 0 to 1: it starts at 1 under `prefers-reduced-motion`, and jumps to 1 the moment the reader picks something. Nothing loops, and only data moves; a day with no honest motion stays still (4 Nov does). `/2026-11-03/viz.js` is the model, and `tools/cards.js` runs with reduced motion, so the images are the finished frame.
- **The exporter always draws the finished frame.** A piece that animates on load sets its animation value to 1 while `CD.exporter.draw` runs and restores it after, so a reader who shares in the first second, or from a background tab, never gets a half-drawn image.
- **Words on the page are for people, not for the record** (the owner's decision, 25 Nov 2026: "so many numbers and small text but it's hard to parse as a human. this is an ongoing pattern"). A reading is the mark's one number and **one plain sentence** a person would say out loud, in normal type, not a stack of uppercase mono lines joined by " · ". Say shares in words ("three in four", "about half"), not "75 of every 100". At most two numbers in a reading. Ranges, rates, method and second findings stay in `data.js` comments unless one of them *is* the point. The overview shows no reading at all; the title already says it. A label on a mark is a name and a number, nothing more. Ask of every line of text: would a reader miss it if it were gone? If not, cut it.
- **Text in the chart is at least 11.5 px** (`11.5 * s`) in IoskeleyMono; chips use 11 px for their context line.
- Register each day in `kit/days.js`. The home grid and the day stepper read that list.
- **Drafts.** A day with `draft: true` in `kit/days.js` is left out of the home grid and the stepper, and its top bar says "Draft". Its URL still works, and adding `?drafts` to any page lists every draft. Remove the flag to publish it.
- **Data is frozen into the day.** Each day's numbers live in its own `data.js`, with sources and timestamps in comments, so the page never depends on another site. `.impeccable/tools/build_data.py` (local only) turned the research files for 6–8 Nov into those `data.js` files.

## The layout of a day: the chart is the page (the user's decision, 12 Nov 2026)

After 3 Nov's first version the user found the visual "very small" with "so much text on the page: two big titles, many footnotes, subtext". Every day made from 13 Nov 2026 on uses the layout of `/2026-11-03/`, which is the model to copy. Days published before that keep the old frame.

- `<body class="cd-day cd-full">`, and the title and dek sit together in `<div class="cd-text">` inside `.cd-head`. The styles are the `.cd-full` block in `kit/cd.css`.
- **One title.** The `<h1>` is the only statement of the point on the page. The sentence in the drawing is drawn **only in shared images** (when `exporting` is true), because those have no title.
- **One sentence of dek,** 150 characters at most, saying what is plotted. No instructions ("pick a year…"): the canvas label and the key hint carry those.
- **One line of source,** 170 characters at most: the one caveat a reader needs, then the source names. Addresses, fetch times and method go in the comments of `data.js`, not on the page.
- **The chart fills the stage** edge to edge (no side margin). At 1024 px and wider the stage also takes the height of the head, and the title block (430 px at most) lies over the chart's top left. `CD.headBox(stage)` returns that block's box, or null on narrow screens where the title sits above the chart. The drawing keeps its marks clear of the box and may use the room under it for a list, a key or the reading; the rest of the canvas is the plot, fitted to the marks, not to a fixed frame.
- **No small print in the drawing on the page:** labels on marks, yes; a second explanatory line, no. The reading appears beside the mark it describes.
- The page check warns when the chart takes less than 42% of the screen's height on a phone, 50% on a tablet or 70% on a desktop, when the dek or source line is over its length, and when the page has no `cd-full` class.

## Adding a day

1. Copy the latest day's folder that uses the `cd-full` layout (`/2026-11-03/` is the first; see "The layout of a day") to a folder named for the new date (for example `2026-11-06/`) and change `data-day`, the title, dek, meta tags and `data-source`.
2. Write `viz.js`: draw into the stage canvas, make the drawing function reusable for export, and wire the reader's reading through `CD.selection` and `CD.bindSelection` (`kit/cd.js`): pointing previews, a click, tap or arrow key pins, Escape and Home go back to the overview, and only the pinned reading goes into the link. Add `readout` to `CD.exporter` so the share panel can name what is shared.
3. Add the day to `kit/days.js`, with `tags`: up to four topic hashtags for its Instagram caption, taken from the day's own keywords (the event, the place, the subject: `tags: ["usdollar", "currencies", "forex", "koreanwon"]`), lower case, letters and digits only, the most specific first. `#dataviz` is added to every post, and Instagram allows five hashtags in a caption.
4. Render its images with `node tools/cards.js YYYY-MM-DD` (a local server on port 8000 must be running). It writes `/YYYY-MM-DD/card.png`, 1200×630 in the day theme, through the same `CD.render` the share sheet uses (the page's `og:image` tags point at it), and, when `cwebp` is installed, the home grid's pictures (`--thumbs` writes only those). A picture is not the share image but the day page's own canvas: the tool opens the page with the bar, title and foot hidden, the margin at nothing and the stage fixed at 480×320 CSS pixels (720×480 for the newest day's `lead.webp` and `lead-night.webp`), in each theme, with motion reduced. So a day needs no extra code for its picture, but its chart must read at phone size, which the day's layout already requires; look at the picture on the home page after rendering. Lead pictures are kept only for the newest published day and any draft after it: the tool deletes older ones. It also writes `/YYYY-MM-DD/ig.jpg`, 1080×1440 (3:4) JPEG in the day theme, the image the Instagram workflow posts (`--ig` writes only that). On Instagram the image stands alone, so a day whose drawing writes no sentence of its own (4 to 9 Nov 2026, marked `noTitle: true` on their exporter) gets the day's title written above the drawing in this image only (`CD.render(w, h, { title: true })` in `kit/cd.js`); a new day writes its own sentence and needs none of this. Render them again whenever the day's data changes.
5. Run `python3 tools/seo.py`. It rewrites the `<!-- seo -->` block in every page's `<head>` (canonical link, the Open Graph and Twitter tags a page doesn't set by hand, JSON-LD: Organization, Article and Dataset for a day, CreativeWork for an archive project), writes the home grid as static HTML so crawlers that run no JavaScript find every day, and regenerates `sitemap.xml`, `robots.txt`, `feed.xml` (RSS) and `llms.txt`. A day's Dataset lists the source URLs it finds in `data.js`, so keep them there. It also stamps each daily page's stylesheet and script addresses with a hash of the file (`/kit/cd.css?v=d523b8f7`), because Pages lets browsers keep a file for ten minutes and a new page with an old stylesheet looks broken; so run it after any change to `kit/` or to a day's `viz.js` or `data.js`, not only after adding a day. `kit/days.js` is stamped on the home page only, since it changes daily and day pages only read their neighbours from it. Drafts get `noindex` and stay out of the sitemap, feed and home grid. Don't edit inside the `<!-- seo -->` blocks or the four site files by hand: the script overwrites them.

## Instagram

A day is posted to Instagram as soon as it is published (the user's decision on 2026-11-19): whoever pushes the day starts `.github/workflows/instagram.yml` for its date once the day is live, `gh workflow run instagram.yml -f date=YYYY-MM-DD`, as the nightly Publish stage does just after midnight in New York. The workflow runs `tools/instagram.js`. Its own schedule (04:07 in New York, then 10:37 and 13:37 UTC) is only a fallback: GitHub started those runs hours late or not at all on 18 and 19 Nov 2026. A day that is already posted is skipped, so the fallback runs do nothing on a normal day. It posts the newest published day dated today or earlier: the day's `ig.jpg`, fetched by Instagram from casualdata.com, so the day must be pushed with its `ig.jpg` first, and a caption made from its `title` and `dek` in `kit/days.js`, with `#dataviz` and the day's own `tags` as hashtags (five at most in all, Instagram's limit since December 2025; a day that lists none gets `#dataviz #datavisualization`). A published caption can't be changed through the API, only by hand in the Instagram app. A day already in a recent caption is skipped, so a second run never posts twice. Run it by hand from the Actions tab (Instagram, Run workflow) with a date to post an older day, `check` to have Instagram check the image without publishing, or `dry-run` to see the caption. Locally: `node tools/instagram.js YYYY-MM-DD --dry-run`.

It needs the repository secret `IG_ACCESS_TOKEN`: the token the Meta app dashboard generates for the casualdata account (Use cases, Manage messaging & content on Instagram, Customize, Generate access tokens). The script accepts both kinds Meta issues and tells them apart by how the token starts. An `EAA…` token comes from *API setup with unified login*, the setup apps created since late 2026 have (ours does); it needs `instagram_basic` and `instagram_content_publish`, its lifetime is set in the app's login configuration (the dashboard's configuration preview shows it), and the workflow can neither refresh it nor read its expiry, so when it runs out the run fails and a new one is generated and stored by hand (`gh secret set IG_ACCESS_TOKEN`). An `IG…` token comes from *API setup with Instagram login* on older apps; it needs `instagram_business_basic` and `instagram_business_content_publish`, lasts 60 days, and is refreshed after each run and stored back with `SECRETS_PAT`, a fine-grained GitHub token for this repository with Secrets: read and write. If an `EAA…` token covers several Instagram accounts, or Meta lists none for it, set the repository variable `IG_USER_ID` to the account's ID. Never commit a token: the repository is public.
